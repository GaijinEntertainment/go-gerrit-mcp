# Return llmxml from every tool that a model reads

- **Date:** 2026-07-10
- **Governs:** `internal/llmxml/`, `internal/tools/`
- **Pinned by:** the golden files in `internal/tools/testdata/`, `internal/tools/error-middleware_test.go`
  (`Test_WrapErrors`)

Tool output reaches a model, which reads named tag boundaries more reliably than JSON quoting or markdown nesting.
Every tool that a model reads returns llmxml from a purpose-built renderer, and the tool that a program reads returns
JSON. The trade: the format is a published contract, so a later change to it breaks the prompts that depend on it.

## Decision

- **llmxml.** Every tool that a model reads returns llmxml: line-structured, semantically tagged text with no schema,
  no declaration, no namespaces, no round-tripping, and no indentation. Emission goes through `internal/llmxml`, never
  `encoding/xml`.
- **Errors in llmxml.** Every in-band tool-call error (argument validation, client-side refusals, Gerrit API
  passthrough) reaches the model as `<error tool="NAME">message</error>`, applied by server middleware for every tool.
  The MCP `isError` flag stays set, and protocol-level failures such as an unknown tool name stay JSON-RPC errors.
- **Recovery path.** When the valid set behind a failed input is known, the error names it: `did_you_mean` proposals
  for file paths, full enumeration for small sets (configured labels, patch-set ranges), and a `hint` that names the
  tool that refreshes stale context (reply anchors). Proposals beyond a similarity threshold are dropped. An empty
  diff for a path that the file list of the revision lacks is an error, and scoped query results name the active
  `scope`. Enrichment fetches run on the failure path only.
- **JSON for a program.** `get_review_activity` returns JSON as text, because a program reads it: the plugin of
  [ADR 2.1](/design-docs/adr/2.1-notification-delivery.md). The `content` field in its result is llmxml, because that
  part reaches the model.

## Why

- Review data nests: per-file comment threads, diff hunks. XML-style tags delimit nested structure with named
  boundaries.
- A serializer built for spec-compliant round-tripping fights line discipline, escaping, and tag shape at every step.
- One dialect for success and failure means that a failure never forces the model to switch parsing mode.
- A far-fetched proposal invites a confident wrong retry.
- llmxml has no schema, so a program cannot parse it reliably.

## Consequences

- User prompts and workflows depend on the shape of the output, so a change to it is a breaking change. Accepted.
- A model that calls `get_review_activity` itself reads JSON. Accepted.

## Rejected

- **JSON for every tool** — quoting, escaping, and depth cost a model attention.
- **Markdown** — it delimits poorly when comment threads and diff hunks nest per file.
- **`encoding/xml`** — built for round-tripping, which this format does not have.
- **`structuredContent` for the tools that a program reads** — it does not reach a mod's `$.mcp.call` (Claude Code
  2.1.330, 2026-11-24).

## Revisit if

Measurements show that models read JSON tool output as accurately and at the same token cost as tagged text. No
measurement backs the current choice; it rests on the reading cost above.
